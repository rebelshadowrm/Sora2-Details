# Map game IDs to meter labels

The [complete command-battle log](../../../docs/COMBAT-LOG-PRIORITY.md) is the primary artifact. Metadata enrichment must preserve raw observations and cannot turn an incomplete action/result stream into a complete one.

Work in the Sora2-Details repository. Read [the table linkage audit](../../../docs/TABLE-LINKAGE-AUDIT.md) before changing lookups. Read [the source-name result](../../../docs/SOURCE-NAMES-AND-CRITS.md) when actor identity matters and [the capture protocol](../../../docs/CAPTURE-PROTOCOL.md) when a label will enter a recorded event. Use [sora2-meter-build](../sora2-meter-build/SKILL.md) for broader capture/UI architecture and [sora2-meter-test](../sora2-meter-test/SKILL.md) for validation-only work.

The current exact-English `table_en.pac` extractors are `tools/name_table_index.py`, `status_name_index.py`, `monster_setting_index.py`, `skill_table_index.py`, and `item_table_index.py`. They hash-check embedded payloads before using build-specific offsets. Recheck the installed archive/build before extending the parser or trusting an offset; do not silently apply this layout to other locales or game versions. The bounded live bridge in `tools/live_capture_bridge.py` now uses the first two tables: direct IDs for five verified party members and a provisional unique six-stat enemy match from per-hit status bytes, with first-seen snapshots as a fallback. Retain its runtime status ID, unit key, and name provenance. The [blind live check](../../../docs/LIVE-METER-20260927.md) correctly labeled three separate Duster Geist instances before the player confirmed the on-screen name; buffed and ambiguous cases remain open.

Keep three links distinct: **live observation → numeric ID or unit key**, **static table join → candidate label**, and **recorded event → displayed label**. Party status IDs `0`, `2`, `4`, `5`, and `6` have live-verified direct `t_name` joins; ID `4` was confirmed by the player as Kloe during the long-running logger session. Other unique party IDs in the exact table may be shown with table provenance while awaiting live validation. Enemy status IDs `60050`–`60052` are live instance IDs, not table keys; `t_mon_mp0000` holds repeated setting rows, and the six-stat `t_status` match is a provisional fallback. Preserve actor instance identity even when names or unit keys repeat.

`t_skill` packs owner and skill ID. The 3:42 PM expanded live capture verified that the effect descriptor at the attack-result path begins with this packed ID for Estelle's True Comet and Shatter Break; descriptor words at `0x10`, `0x20`, and `0x30` also match the exact English rows. `tools/live_capture_bridge.py` joins those fields and leaves missing/ambiguous cases unknown. This identifies **damaging hit results**, not selected no-HP actions or misses. Seven packed IDs have two rows, so require a unique full-parameter match. `t_item` has unique IDs and Tear Balm's row has a 1,500 candidate value, but no live item ID has been captured. Do not turn a table value into a resolved hit/heal, infer physical versus Arts from animation, or infer critical status from magnitude.

For UI icons, `tools/build_skill_icon_map.py` derives a category or Art element from exact `t_skill` `rawParam10` values and omits unresolved packed IDs. `tools/extract_meter_icons.py` hash-checks the installed `image.pac` index, selected UI textures, and AT face-strip payloads, then extracts PNG symbols and 11 party portraits to LocalAppData. This is presentation metadata, not a damage-class decoder. `SkillPowerIcon` encodes power-rank letters, not per-skill images. `t_name` has a face-model key at offset `0x18` joining to `.mdl`, and a separate character-model key at `0x20` whose numeric suffix joins to `at_cXXXX.dds` turn-bar portrait strips. Keep name/status/model/portrait joins distinct; Julia and Mueller lack a verified portrait join.

For damage-class research, use the player-confirmed same-actor controls in [the damage-type comparison](../../../docs/DAMAGE-TYPE-AND-CRIT-20260927.md): physical-damage Craft Shatter Break, Arts-damage Craft True Comet, and Lightning Art. Each produced raw result flag `0x52000` on at least one hit; the flag cannot identify category or damage class. The exact skill table's raw row word `rawParam30` is `0xE` for Shatter Break and `0xF` for True Comet and Lightning; ordinary Attacks have `0xC`. The live bridge provisionally classifies those codes after a unique skill-row join and records provenance. Other codes remain Unknown. Source context `+0x30` correlates with Agate normal-Attack crits but fails on a player-confirmed critical Stone Hammer with a triggered follow-up; preserve it as raw data, never as a general crit label. Do not use damage magnitude as a substitute.

Enemy packed effect IDs can use the runtime instance ID in the high half and a local AI skill ID in the low half. The exact English `script_en.pac` has per-monster `ai_{unitKey}.dat` files with `SkillTable` ID/name entries; use hash-gated `tools/enemy_ai_skill_index.py` and [the AI audit](../../../docs/TABLE-LINKAGE-AUDIT.md). The bridge displays an enemy move only if the live stat signature yields one exact unit key and the AI script yields one name for the low ID. Prefix `?` and retain provenance because the unit key is still inferred from stats, not directly read. When several unit keys share stats (runtime enemy `60030` did), leave the move Unknown even if each script has a plausible name. Keep raw effect ID/code for future direct unit-key research.

The [2026-09-28 ambiguous-main-enemy case](../../../docs/HEAL-AND-ENEMY-LOOKUP-GAPS-20260928.md) showed uniquely named adds beside a main enemy whose signature matched two rows. Current encounter snapshots retain `nameLookupSignature` and every exact `nameLookupCandidates` pair (`unitId`, `name`) for future cases. A player's partial recollection of an add does not resolve the main enemy. Preserve both candidates, the numeric runtime ID, and the unresolved display label until a direct runtime unit key or independent exact on-screen confirmation distinguishes them. Historical snapshots made before these fields existed cannot reconstruct candidate names when their raw trace is missing.

When implementing a lookup, return the observed key, candidate label(s), build/locale provenance, and explicit resolved/ambiguous/unknown state. Keep lookup failure visible so the meter does not present a guessed name as captured fact. Validate known positive joins and negative/duplicate cases using the exact archive; compare a label against an independently reported live action before claiming automatic attribution. Run the solution build and focused checks after integration changes.

For an offline regression against this installed English archive, run `python tools/check_table_linkage.py 'C:\Games\Trails in the Sky 2nd Chapter\pac\steam\table_en.pac'` and `python tools/test_live_capture_bridge.py`. The cross-table checks are static; they do not replace a blind live enemy-name test or a verified runtime move ID.
