# Build the command-battle combat log

The [advanced combat log](../../../docs/COMBAT-LOG-PRIORITY.md) is the primary product. Treat the meter as a derived view. Before adding more display features, prove an ordered, durable action-and-outcome stream with explicit unknown events and coverage gaps; an HP-total match alone is not completeness.

Work in the Sora2-Details repository. Read the relevant parts of [the build plan](../../../BUILD-PLAN.md) and [README](../../../README.md) before changing architecture. Read [the hook research handoff](../../../docs/HOOK-RESEARCH-HANDOFF.md) when the task touches game capture, executable addresses, or skill metadata. Inspect the current code before treating a planned component as already implemented.

For the current installed preview, `tools/lifecycle_probe.py` writes bounded raw JSONL under `%LOCALAPPDATA%\Sora2 Details\live`, and `tools/live_capture_bridge.py` writes partial encounter snapshots under `%LOCALAPPDATA%\Sora2 Details\encounters`. Keep raw evidence durable across app updates and distinguish the Python bridge from the fuller `ICombatCaptureSource` design. Use [sora2-meter-publish](../sora2-meter-publish/SKILL.md) when packaging or publishing builds.

## Product invariants

- Capture **command battles only**. Start with the verified command-battle boundary and entry HP/status state; exclude earlier field effects.
- Record executed actions independently of HP writes, including support moves, misses, canceled actions, and other no-HP outcomes when observed. Keep per-target results and repeated hits distinct under their parent action; preserve unknown raw codes rather than dropping them.
- Keep the compact meter usable with replay data while capture is developed. Damage, Healing, Taken, Deaths, recent ten fights, More history, timelines, and per-knockout recaps all derive from the same ordered event stream.
- Attribute each resolved effect to an encounter, action, source actor instance, and target actor instance when observed. Represent missing source, move, class, or amount as unknown, and mark partial/gapped encounters. Do not infer a killer or physical/Arts class from animation alone.
- Keep stable actor identity separate from the human-readable name. For name research, trace a verified actor/status pointer to a game ID or name field, then validate the ID against the current localized table and at least two live actors; preserve unnamed enemy instances when unresolved.
- This exact English `t_name.tbl` has direct ID/name/status-key rows for the five live-verified party IDs `0`, `2`, `4`, `5`, and `6`; ID `4` is player-confirmed Kloe. `tools/name_table_index.py` is hash-gated. Use this stronger party lookup when those live IDs are observed. The enemy instance IDs `60050`–`60052` are absent from that table and still require a separate verified unit key or provisional status-signature match.
- This build's `t_skill` packed owner/skill ID, `t_item` item ID, and `t_mon_mp0000` unit-key joins are decoded in [the table linkage audit](../../../docs/TABLE-LINKAGE-AUDIT.md). The expanded result probe now captures a live packed skill ID and verifies its descriptor fields against exact English `t_skill` rows for damaging hits. This does not yet identify selected no-HP actions, misses, enemy effect IDs absent from this table, live item IDs, or a monster-setting pointer. Keep duplicate skill IDs and repeated monster-setting keys ambiguous; never infer a live amount from static metadata.
- The current exact-English-table research matcher can resolve enemy names from a unique six-field status signature (level, EXP, EP, DEF, ADF, MOV). Treat this as provisional metadata, keep each status pointer as the actor instance ID, and return unknown on zero or multiple table matches. Validate buffs and level/difficulty changes before using the signature in a production adapter; prefer a direct runtime unit key if found. See [source-name research](../../../docs/SOURCE-NAMES-AND-CRITS.md).
- Treat critical hit as a per-result, nullable observation. Look for a flag on the verified attack-result path and compare a controlled normal hit with a controlled critical hit on that same path. Never infer a critical from damage magnitude, an overlay, or a player's rough damage estimate. Retain provenance for names and critical status in research replays.
- The [2026-09-27 result comparison](../../../docs/DAMAGE-TYPE-AND-CRIT-20260927.md) found `0x52000` on physical Shatter Break, Arts-damage True Comet, and Lightning; the raw flag alone cannot classify them. The bridge provisionally uses uniquely matched skill-row effect codes `0xC`/`0xE` as Physical and `0xF` as Arts, with explicit provenance, and retains Unknown when no code is validated. Exact `0x42000` remains a fallback for ordinary Physical Attacks; it occurs on both crits and non-crits. Two player-controlled Agate normal-Attack fights correlated source context `+0x30` value `3` with reported crits and `1` with non-crits. However, a player-confirmed critical Stone Hammer with a triggered follow-up also had value `1`, the same as a non-critical Stone Hammer. Preserve the raw source-context word but leave automatic `IsCritical` null; neither result flag nor context word is a validated general critical detector.
- A later same-target Air Strike sequence gave target status `+0x7C = 0` on a reported non-crit and `3` on two reported crits, but a following battle ended with a player-confirmed **non-critical** Stone Hammer for which both source `+0x30` and target `+0x7C` were `3`. The earlier two reported crits in that fight fell inside a capture restart gap. Preserve both raw fields and keep `IsCritical` null; trace the game's actual per-target critical decision or display path before decoding.
- For live name research, decide which context, status, and linked-object bytes are needed before arming a probe. Gather them in one bounded, hash-gated elevated run; avoid a new administrator prompt for each follow-up read. Stop live probing when the player reports prompt fatigue and continue from saved evidence.
- Distinguish resolved amount from effective HP change and retain both when available. Avoid overkill/overheal inflation in default effective totals. Count one result per target application, not per visual hit or target animation.
- The current attack-result hook verifies some damaging hits, while the shared HP setter observes healing without a verified source, item, move, or support-proc identity. Keep ability and random-proc heals unattributed until a captured execution/effect context proves their source. Preserve HP-setter frame evidence and compare a controlled heal with a proc heal; do not assign the nearest preceding action. See [the heal/lookup gap audit](../../../docs/HEAL-AND-ENEMY-LOOKUP-GAPS-20260928.md).
- Display damage totals first. Add DPS only after defining and validating the time base across menus, pauses, animation speed changes, and encounter transitions; label its time basis.

## Capture decisions

For startup/elevation or distribution-footprint work, use [distribution UX](../sora2-meter-distribution-ux/SKILL.md). The installed launcher elevates `Sora2.Details.CaptureHost.exe`, not the desktop/updater. Its fixed bundled-Python child reports both host and server PIDs; preserve the initiating user's data path across elevation. Validate readiness changes with `python -m unittest discover -s tools -p test_elevated_probe_session.py` without attaching to the game.

The handoff contains **static leads**, not verified hooks. Recheck the local EXE SHA-256 before using an RVA. Prove lifecycle and an attributed HP result in a controlled fight before shipping a native adapter. In particular, `btlcom.OnAttackHit` is a script lookup reference and is not yet a confirmed damage event. If a candidate lacks source, target, move, or final amount, trace toward the resolved HP write or correlate it with a verified action context. Keep unsupported EXE versions from using unchecked offsets.

Use `ICombatCaptureSource` and the event records in `src/Sora2.Details.Core` as the current integration seam. The v1 encounter assembler, recorder, durable store, and desktop wiring already exist, but their effect-only protocol is incomplete for a full combat log. Evolve that protocol when verified runtime data warrants it, keeping raw action and result observations independent of HP changes. Keep capture work off the game's critical path and expose dropped events rather than silently presenting incomplete totals. Preserve the sample replay as a development input.

## Completion evidence

Run `dotnet build Sora2.Details.sln -c Release` and `dotnet run --project tests/Sora2.Details.Checks -c Release` after implementation changes. Add focused checks for changed calculations or lifecycle behavior. For live capture work, record what was directly observed, the executable fingerprint, and which fields remain unverified. Report the resulting behavior and the next concrete gate when the feature is still limited by missing runtime evidence.
