# Source names and critical hits: research gate

Updated 2026-09-26. Scope: command-battle results on the exact `sora_2nd.exe` SHA-256 `D8B2911D1576216BDC22D070550E4F531E105DE7ED2981885849669F4ACF8AAF`.

## Lookup-matching result

The exact English `t_status.tbl` payload was decoded using the [KuroTools Sora2 StatusParam schema](https://github.com/nnguyen259/KuroTools/blob/master/schemas/headers/StatusParam.json), then independently read by [status_name_index.py](../tools/status_name_index.py), which checks the payload SHA-256 before using row offsets. It contains **503 unique unit keys** and human-readable names. The party block begins at row 471.

A bounded, read-only [live status snapshot](../samples/research/status-identity-20260926.jsonl) found first-dword status IDs `0`, `2`, `5`, and `6` for the already-confirmed Estelle, Scherazard, Agate, and Tita instances. Their max HP values match the player's earlier reports: 5,859, 5,973, 6,682, and 6,904. The first lookup used `t_status` rows `471 + ID`; [match_status_snapshot.py](../tools/match_status_snapshot.py) now uses the stronger direct `t_name` ID → status unit key → `t_status` join and produces the [four live party matches](../samples/research/party-name-match-20260926.json), with table and pointer provenance recorded. This verifies those four IDs, not every possible party variant.

Offline follow-up on 2026-09-27: the exact English `table_en/t_name.tbl` is indexed at PAC data offset `0x35BBD0`, 255,068 bytes, SHA-256 `6101d18a87112e351c2ba1009933cc77b660630a0497c33d9119a81a9916c548`. Its `NameTableData` section has 1,583 fixed-size rows, including numeric character ID, display-name string offset, and status-unit-key string offset. The hash-gated [name_table_index.py](../tools/name_table_index.py) reads it. **IDs `0`, `2`, `5`, and `6` directly yield Estelle/`chr5000p`, Scherazard/`chr5002p`, Agate/`chr0005p`, and Tita/`chr5006p`**, matching both the live status IDs and the earlier `t_status` row lookup. This is stronger evidence for these four party names than the `471 + ID` row heuristic. The table has repeated IDs (notably placeholder `65535`), so the lookup accepts only unique IDs. Observed enemy instance IDs `60050`–`60052` have no rows in this table; the provisional enemy stat-signature method is still needed until a direct enemy unit key is found.

The broader [table linkage audit](TABLE-LINKAGE-AUDIT.md) found that monster-setting rows carry unit keys that join to `t_status`, including `mon5014_c02` and `mon5003`. Multiple setting rows share each key; none is yet proven to be reachable from the captured live enemy context. It also maps static skill owner IDs through `t_name` and item IDs through `t_item` for future action lookup.

In a later command battle, the player identified an enemy as **Emeronecider** and used Agate's normal Attack. The [bounded attack trace](../samples/research/actor-name-live-20260926.jsonl) paired source status pointer `0x16c50ee5588` (Agate) with enemy status pointer `0x16c26163730` and HP `165585 -> 162074`, a **3,511** loss. The enemy status object's first dword was `60050`; this is a runtime instance ID, not row 173 or a decoded unit key. The first probe detached cleanly, and the game remained responsive.

The same battle also contained two **Lily Mover** enemies. A later [attack trace](../samples/research/probe-session-f34d659763c2419e8905994d22040fbd.jsonl) captured Scherazard applying **3,354** to runtime status `60052` and **865** to Emeronecider `60050` at the same moment, consistent with the player's observation that the attack also reached Emeronecider. The source and target status snapshots exposed level, EXP, EP, DEF, ADF, and MOV. For monsters, those values can be computed from each status-table row as `(level, trunc(exp_base + level * exp_growth), ep, trunc(def_base + level * def_growth), trunc(adf_base + level * adf_growth), trunc(mov_base + level * mov_growth))`. The captured tuples are `(54,301,1000,361,321,6)` for `60052` and `(55,923,3000,921,272,7)` for `60050`. Each tuple matches **one** of the 503 rows: `mon5003` / Lily Mover and `mon5014_c02` / Emeronecider respectively. [match_enemy_status.py](../tools/match_enemy_status.py) accepts a name only on a unique exact match; it does not pick the nearest row.

A later [read-only status scan](../samples/research/probe-session-af83e1072df744b1afdfda97cca9d4ce.jsonl) found all three enemy instances: `60050` / Emeronecider, `60051` / Lily Mover, and `60052` / Lily Mover. The [three-enemy lookup result](../samples/research/three-enemy-name-match-20260926.json) preserves separate pointers and HP values for both Lily Movers. This independently agrees with the player's three on-screen names and demonstrates that identical display names need not merge instances. The stat-signature method is a **provisional research lookup**, not a verified runtime unit-key pointer: buffs, level scaling, reused IDs, and table updates need negative controls before automatic production use. Across the exact table, 403 of 503 rows have a unique signature; ambiguous matches correctly remain unnamed.

Fresh [context](../samples/research/status-context-whole-20260926.jsonl) and [full status](../samples/research/status-full-20260926.jsonl) snapshots found no direct unit-key string in the enemy's 0x2A0-byte status record or first 0x600 context bytes. Following selected context links also found no direct `mon5014_c02` string in their first bytes. These are bounded negative observations, not proof that a direct key is unavailable elsewhere.

## What the present log proves

The [attributed attack trace](../samples/research/attack-source-20260926.jsonl) records a source context, target context, candidate resolved amount, and paired target HP setter on one attack-result path. The first pointer in each context led to a status instance. In the selected command interval, all 13 attack calls paired with 13 HP setter calls and the controlled Agate hit reconciled to 10,452 effective damage. Thus a source **instance** is available on this path.

The earlier [research pointer map](../samples/research/attributed-actor-map-20260926.json) assigns the four party names from the player's confirmed roster and earlier HP observations. That older replay has not been retroactively relabeled; the new lookup scripts are separate research tools. Addresses are session-specific and cannot serve as a permanent name database.

The English archive `C:\Games\Trails in the Sky 2nd Chapter\pac\steam\table_en.pac` contains `table_en/t_status.tbl` at archive data offset `0x647B9F`, 546,548 bytes. The table may contain multiple variants and localization differences; a display name alone cannot distinguish two same-name enemies.

The game archives also contain the words `Critical`, `Critical UP`, and `CRITICAL`, but these strings occur in other contexts such as a skill name, buffs, and a turn bonus. Their presence does not identify a per-hit critical flag. The current attack trace did not snapshot a candidate critical field. The player's report that a critical overlay obscured the last two digits of Agate's `104xx` hit supports annotating that one observed hit as player-reported; it does not validate an automatic game-data flag or classify other hits.
