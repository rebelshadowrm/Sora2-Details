# Distribution and elevation audit (2026-09-29)

## Launch and privilege boundary

The production app requests elevation before creating the WPF app or main window. Direct executable startup relaunches the same executable with the `runas` verb; Windows displays its normal approval prompt without a separate information dialog. `Start-Sora2Details.ps1` opens the app first for standard-user launches, so the Windows approval prompt identifies Sora 2 Details; the app's elevated process then starts the capture scripts. The app passes `--data-dir` across the elevation boundary so an alternate administrator profile does not silently redirect its history and traces. The app is elevated even when the game is not running or the user opens saved history; canceling startup approval ends startup without another app dialog.

The tray is the persistent surface and contains the **Start capture** and **Stop capture** commands. The meter shows capture state but has no separate capture button. If exactly one game process is already running, the app attempts startup capture after approval. With no game, it hides the meter and waits in the tray. A later game launch triggers **Game detected — Start capture?**; clicking the notification or choosing **Start capture** from the tray menu begins capture. If multiple game processes are running, capture stays stopped until only one remains and the player chooses Start. When the captured game exits, the app waits for the trace's target-exit/detach result and for the bridge, Python service, and CaptureHost processes to exit; then it clears the active session record, hides the live meter, and remains in the tray. Starting the game again produces a new explicit Start choice. Launching the EXE while the app is resident restores the same meter from the tray. The tray Settings command and meter settings entry open a window; the X button asks whether to hide the meter in the tray or exit, with an optional remembered choice that can be cleared in Settings; the tray uses the packaged app icon.

The live probe is bounded to at most 12 hours or 2,000,000 watched hits. At a bound it detaches cleanly; the elevated app remains resident. It does not silently reattach after a capture bound while the same game remains open. The tray's Start command remains available to begin another session.

The standard-user-first path is diagnostic-only: `tools/start_probe_session.ps1 -TryUnprivileged` must be run from a standard-user shell and never retries with elevation. Normal release startup does not probe and then prompt later. After the one startup approval, PowerShell, `CaptureHost.exe`, bundled Python, the probe, and live bridge use direct child-process creation (`UseShellExecute = false`) without `RunAs`; they inherit the app's elevated token. `CaptureHost.exe` rejects a non-elevated parent rather than opening another UAC prompt. This is not an installer privilege requirement. No privileged service or scheduled task is installed.

The **↻** button only checks for updates. Applying an available update is a separate click. If capture is active, the app explains that it will detach and restart, then asks for confirmation. After confirmation it writes the stop marker and waits for the trace detach/target-exit event and for the bridge, Python service, and CaptureHost processes to exit. Only then does it download and apply the update. `SetAutoApplyOnStartup(false)` prevents a staged update from applying during launch. In Velopack 1.2.158, `UpdateManager` starts Update.exe through the locator's ordinary `Process.Start` path (no `RunAs` verb); Windows gives that child the elevated parent's process token, and the updater starts the restarted app from its own existing process chain. Restart arguments preserve the selected data directory, capture duration, game path, Python path, and meter-only option. The package is self-contained, so it has no framework prerequisite installer expected to request separate approval. This token-inheritance conclusion is source-audited; an installed update still needs owner testing to verify the complete interactive chain.

## Process access audit

The memory-reading calls now use the smallest handle rights required by each operation:

| Call site | Requested access | Reason |
| --- | --- | --- |
| `lifecycle_probe.image_path` | `PROCESS_QUERY_LIMITED_INFORMATION` (`0x1000`) | `QueryFullProcessImageNameW` for the hash gate; no memory access. |
| `lifecycle_probe.trace` | `PROCESS_VM_READ` (`0x0010`) | Its dedicated handle is passed only to `ReadProcessMemory`. |
| `read_status_identity.py` | `PROCESS_VM_READ` (`0x0010`) | It calls `ReadProcessMemory`; executable path lookup uses the separate limited-query handle. |
| `hp_memory_probe.py` read/watch modes | `PROCESS_VM_READ` (`0x0010`) | These modes call `ReadProcessMemory` only. |
| `hp_memory_probe.py` full scan; `scan_status_instances.py` | `PROCESS_VM_READ \| PROCESS_QUERY_INFORMATION` (`0x0010 \| 0x0400`) | These modes enumerate regions with `VirtualQueryEx`; Microsoft requires `PROCESS_QUERY_INFORMATION` for that query. |

No source call requests the `PROCESS_ALL_ACCESS` constant, and the application does not open its token or enable `SeDebugPrivilege`. `ReadProcessMemory` itself needs only `PROCESS_VM_READ`; `VirtualQueryEx` is the only memory-reader operation that adds `PROCESS_QUERY_INFORMATION`. `PROCESS_QUERY_LIMITED_INFORMATION` is used separately for the executable path.

The live capture still attaches a debugger: `lifecycle_probe.py` calls `DebugActiveProcess(pid)`, installs/restores hardware breakpoints through `SetThreadContext`, and uses debug events. Although that call takes no access-mask argument in our code, Microsoft's contract says it must be able to open the target with `PROCESS_ALL_ACCESS`; its process debug-event handle also carries `PROCESS_VM_READ | PROCESS_VM_WRITE`, and thread event handles carry context-read/write and suspend/resume rights. We keep that handle for debugger control and pass a separate `PROCESS_VM_READ` handle to all game-memory reads. The probe does not call `WriteProcessMemory` or write game memory, but this event-driven capture is not equivalent to a pure read-only `OpenProcess` reader. Replacing debugger hooks with polling would be a separate capture redesign and would lose the currently observed event path.

Administrator elevation is not inherently required by `ReadProcessMemory` when the target DACL grants the requested rights. Historical real-game measurement recorded `OpenProcess(PROCESS_VM_READ)` failing with Windows error 5 (`ERROR_ACCESS_DENIED`), while `PROCESS_QUERY_LIMITED_INFORMATION` succeeded; the elevated read-only scan then succeeded. Because live capture is the primary app function and this game-specific denial is known, the release now establishes elevation at startup instead of waiting to identify which operation will fail in each session. There is no later elevation fallback. If a necessary operation still fails under the elevated app, capture reports that API error without presenting another UAC prompt. The current machine had no running game during this UX follow-up, so the historical error-5 result was not repeated on 2026-09-29.

Microsoft API references: [ReadProcessMemory](https://learn.microsoft.com/en-us/windows/win32/api/memoryapi/nf-memoryapi-readprocessmemory), [VirtualQueryEx](https://learn.microsoft.com/en-us/windows/win32/api/memoryapi/nf-memoryapi-virtualqueryex), [process security and access rights](https://learn.microsoft.com/en-us/windows/win32/procthread/process-security-and-access-rights), [DebugActiveProcess](https://learn.microsoft.com/en-us/windows/desktop/api/debugapi/nf-debugapi-debugactiveprocess), and [debugging events](https://learn.microsoft.com/en-us/windows/win32/debug/debugging-events).

## Windows trust and release signing

UAC consent, Authenticode publisher identity, SmartScreen reputation, and Smart App Control are separate. An icon and product description improve recognition but do not establish a trusted publisher. The local preview remains unsigned until an actual signing identity is configured.

`tools/build_installer.ps1` accepts `-SignParams` or `VPK_SIGN_PARAMS`, forwarded to the pinned Velopack CLI. Use `-RequireSigning` for a distribution build that must not silently fall back to unsigned output. It rejects missing configuration before building and verifies the delivered portable desktop/helper/updater and final Setup signatures after packaging. Use certificate-store or managed signing credentials; do not commit private keys or put passwords in command arguments. Signing is performed by Velopack so its Setup/updater binaries are covered at the appropriate build stages, rather than signing only the desktop or signing Setup after packaging. CI must provision the signing tool, identity and credentials before enabling the gate; this change does not provision an account or credentials.

Microsoft says unsigned versions must accumulate reputation separately, while a consistent signing identity can carry publisher reputation across releases. Signing does not guarantee a warning-free first download. Microsoft's current guidance explicitly says EV certificates no longer receive an automatic SmartScreen bypass; the Velopack signing page still contains older conflicting claims. Prefer Microsoft's guidance for reputation and Velopack's documentation for packaging mechanics.

## Build and runtime findings

- Keep the .NET/Python bundle: it removes prerequisites from a friend's install. The helper is trimmed independently; WPF is not a suitable target for blindly enabling trimming. Both use self-contained single-file publishing, which can extract native libraries on first launch. Measure cold startup before changing that tradeoff.
- Installed scripts are allowlisted, Python is pinned by SHA-256, and saved data lives outside version replacement. Preserve these existing strengths.
- The helper adds a small process and bundled runtime footprint; this is a UX improvement, not a claimed CPU optimization. It sleeps while its child runs and exits with the session.
- The bridge reads the raw trace incrementally with a 100 ms idle wait. It also rewrites the full encounter JSON on saves. Long fights can therefore increase serialization and UI reload work. A future measured optimization is batching derived snapshots while retaining immediate raw evidence and flushing at encounter end/detach. Do not weaken durability merely to reduce writes.
- The startup approval occurs before game lookup and all capture compatibility checks. The several separate Python metadata checks and executable/table hashes run after approval as compatibility gates; combining them could reduce interpreter startup overhead, but caching solely by file path would weaken patch rejection. No benchmark currently establishes them as a meaningful delay.

Run the Release solution build and existing .NET checks, then `python -m unittest discover -s tools -p test_elevated_probe_session.py` and `python tools/test_lifecycle_probe.py`. The readiness test uses a temporary directory and mocks target verification, including the error-5 startup signal used for reporting startup failures. The lifecycle check uses a disposable synthetic process and confirms attach/hit/detach with the VM_READ-only memory handle; neither test attaches to the game. Those checks predate the current startup-elevation and update-flow changes.

Build a local preview into an isolated output directory. The builder smoke-tests the packaged helper with `--check-package` without UAC. Inspect the portable ZIP for the helper, embedded runtime, fixed runtime script allowlist, icon and absence of local data. Regenerate the code-drawn multi-resolution ICO with `tools/build_app_icon.ps1`.

Before public release, manually check: Windows shows one startup UAC prompt without a separate app dialog; cancellation causes no follow-up app popup; launching the EXE while the app is hidden restores the existing meter; the X prompt offers hide or exit and remembers only when checked; Settings can clear a remembered choice; direct EXE and CMD/PowerShell launch each produce only one UAC prompt; CaptureHost, Python, and the bridge launch without additional prompts; automatic startup attach when the game is already running; game-absent tray waiting followed by the late-game notification and explicit Start choice; the meter reports Starting capture only while connecting and Capturing once a session is active; game exit cleanup and a later new-PID Start; hide/show; click-through recovery; history/settings tray commands; and explicit Exit leaving no desktop, CaptureHost, bridge, or Python helper. Also check an in-app update during active capture, including confirmation, detach, update, restart, preserved encounters/launch settings, and the absence of a second UAC prompt. Existing CloseToTray values are ignored so prior default values do not suppress the new prompt. The dialog also leaves full shutdown available from the tray without prompting.
