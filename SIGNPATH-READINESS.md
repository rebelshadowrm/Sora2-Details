# SignPath Foundation readiness

Review date: 2026-09-29. This records repository-side preparation against the [current SignPath Foundation terms](https://signpath.org/terms.html) and [SignPath GitHub Trusted Build documentation](https://docs.signpath.io/trusted-build-systems/github). It does not claim an application has been submitted or approved. No SignPath identifiers, credentials, tokens, or certificates have been added.

## Repository requirements satisfied

- **OSI-approved project license:** added the MIT license in [`LICENSE`](LICENSE), identified it in the README, and included it with the policy in both the Velopack and legacy ZIP packages. No conflicting project license statement was found in the repository review.
- **Code signing policy:** [`CODE-SIGNING-POLICY.md`](CODE-SIGNING-POLICY.md) contains the required exact SignPath attribution, current single-maintainer roles, privacy/network behavior, provenance, intended signing scope, and capture security details. The README and release notes link to it using the exact term “Code signing policy.”
- **Privacy disclosure:** source review found an automatic GitHub Releases update check when the desktop window loads. A second check is user-initiated; downloading and applying an update are user-initiated and require confirmation while capture is active. The policy names GitHub, describes ordinary connection metadata, and says encounter data, traces, and game-memory data are not uploaded by the app. No other application runtime network destination, analytics service, or crash-upload service was found in the reviewed source. Build-time Python/.NET/GitHub traffic and future SignPath submission are disclosed separately.
- **Build provenance and signing flow:** `.github/workflows/preview-release.yml` builds and runs the repository checks on `windows-latest`, creates unsigned release outputs, uploads the prepared artifact with `actions/upload-artifact` before the conditional SignPath step, retrieves signed output, verifies signatures, and publishes only after prior steps succeed. The unsigned preview path remains active when `SIGNPATH_ENABLED` is unset/false. This matches the documented GitHub artifact-upload prerequisite; the workflow is not yet exercised against a SignPath project.
- **Signing scope and metadata rules:** [the artifact configuration](.signpath/artifact-configurations/velopack-preview.xml) scopes signing to the Setup installer and the project's Desktop/CaptureHost executables in the portable and full update packages. It constrains product name/version and numeric file version for the two project executables. It was checked against SignPath's artifact-configuration XSD. Upstream Velopack/CPython executables are excluded from signing.
- **Deterministic version metadata:** `tools/build_installer.ps1` passes the release SemVer to product and informational version metadata and maps its numeric major/minor/patch to a four-part Windows file version. The build asserts product name, product version, and file version for both published project executables. Prerelease text remains in product/informational version values.
- **Uninstallation:** the README documents uninstall through Windows Settings and explains that local user data remains. The build check extracts the packaged Velopack `Update.exe` and confirms its help exposes `Update.exe uninstall`; Velopack documents its Windows Setup/Apps & Features integration and updater uninstall command ([installer docs](https://docs.velopack.io/packaging/installer), [Update.exe reference](https://docs.velopack.io/reference/cli/content/update-windows)). The portable ZIP is documented as removable by deleting its folder.
- **Capture security disclosure:** the policy states the supported-executable SHA-256 gate; read-only game-memory access; no game-memory writes, injection, code patching, or anti-cheat/security bypass; the purpose of `DebugActiveProcess`, elevation, and hardware debug-register watchpoints. These are documentation changes; capture behavior was not changed for this work.
- **Existing published/download documentation:** README and release notes describe the application and link to the policy from the download/release information.

## SignPath approval and configuration required

- Submit the Open Source Code Signing application and wait for an explicit SignPath Foundation decision. Approval and certificate availability are not assumed.
- After approval, create/configure the SignPath organization/project, signing policy, artifact configuration, GitHub.com Trusted Build System, and required repository integration. SignPath's current GitHub docs call for the predefined GitHub.com trusted build system and require GitHub-hosted jobs leading to signing plus a GitHub Actions artifact uploaded before submission ([GitHub integration requirements](https://docs.signpath.io/trusted-build-systems/github)). Install/link the SignPath GitHub App if required for the selected audit-log policy.
- Import the checked-in XML artifact configuration into SignPath and set its resulting configuration slug. Configure the organization ID, project slug, signing-policy slug, and API token in GitHub Actions variables/secrets using values issued by SignPath. Then set `SIGNPATH_ENABLED=true`. The workflow references these named configuration points but does not define their values.
- Preserve manual approval for every release signing request. Run a new tagged preview after configuration and inspect the SignPath request, provenance, signed outputs, Authenticode verification, package feed hashes, and published assets before treating the integration as production-ready.

## Remaining risks and blockers

- **Approval/configuration blocker:** there is no SignPath approval, project, policy, token, certificate, or signing-enabled workflow run yet. Current releases therefore remain unsigned. Signing cannot be validated end to end until those external steps are complete.
- **Hosted settings unverified:** GitHub MFA, rulesets, tag protection, and SignPath account settings are external to this checkout and have not been asserted as configured.
- **Updater choice/installer UX:** the app sends an automatic release-check request to its documented GitHub endpoint on startup and currently has no setting to disable that check. The one-click Velopack Setup has no install wizard/options. The behavior is disclosed in the policy and the update payload is user-initiated, but the owner should ask SignPath whether its privacy condition requires an install-time notice or an opt-out for this request behavior; add an app/installer option if SignPath requires one.
- **Eligibility judgment:** capture uses `DebugActiveProcess` and hardware debug registers to observe a supported game's state. The audited implementation is read-only for game memory and does not inject or bypass protections, but SignPath Foundation makes the final eligibility decision under its “No hacking tools” condition. Discuss this behavior transparently in the application rather than changing capture semantics for this readiness work.
- **Third-party coverage:** the artifact configuration intentionally does not sign upstream Velopack or CPython executables. SignPath currently permits unsigned upstream OSS binaries inside signed packages, while reserving the possibility of stronger signing-coverage requirements. The owner must confirm component eligibility and reassess if those terms change.
- **Legacy ZIP:** the separate ZIP-only builder remains outside the SignPath workflow and produces an unsigned archive; README and policy identify it as a legacy path.
- **Interactive uninstall:** Velopack's packaged updater exposes `uninstall`, and the installer is documented to register in Apps & Features; an interactive install/uninstall test remains outstanding.
